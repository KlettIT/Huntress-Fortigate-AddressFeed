# Huntress-Fortigate-AddressFeed

External IPv4 address feed for FortiGate (external IP address feed) for the
Huntress EDR agent domains. The feed is generated by GitHub Actions from
`sources.txt` and pulled by the FortiGate from:

```
https://raw.githubusercontent.com/KlettIT/Huntress-Fortigate-AddressFeed/main/feed.txt
```

## Background

Huntress EDR agents communicate with a fixed set of domains (agent,
update, CDN, S3/Azure blob storage, bugsnag, GitHub raw content). In our
environment, DNS does not pass through the FortiGate (our internal DNS
server resolves locally), so FortiGate FQDN address objects are not
populated. Instead, this repo maintains a static IPv4 list that is
resolved by GitHub Actions and imported into FortiOS 7.6 as an external
IP address feed.

## Pipeline

```
sources.txt  --push-->  GitHub Actions (dig, dedupe, merge)
                                    |
                                    v
                              feed.txt (committed back to this repo)
                                    |
                                    v
              FortiGate external IP feed (pull, every 1800 s)
                                    |
                                    v
                     firewall policy (dstaddr, TCP 443)
```

## Files

| File | Purpose |
|---|---|
| `sources.txt` | Maintained domain list (one domain per line, `#` comments allowed) |
| `feed.txt` | Generated feed (plain IPv4 list, deduplicated) – pulled by the FortiGate |
| `.github/workflows/feed.yml` | GitHub Actions workflow |

## GitHub Actions

**Triggers**

- Push to `sources.txt` → immediate rebuild
- Schedule: every 2 hours (`cron: "0 */2 * * *"`), GitHub may delay scheduled runs by a few minutes
- `workflow_dispatch` → run manually (e.g., after changing domains)

**Workflow steps**

1. **Resolve**: `dig +short A` is run for every domain in `sources.txt`
   (timeout 5 s, 2 retries); only clean IPv4 records are kept
   (CNAME lines are filtered out). Domains without an answer log a
   `WARN` entry.
2. **Guard**: If fewer than 10 fresh IPs are resolved (e.g., DNS
   outage), the workflow aborts – the previous `feed.txt` is kept.
3. **Merge**: New IPs are unioned with the last committed `feed.txt`.
   This prevents rotating CDN IPs (CloudFront, S3, Azure) from
   churning between runs – otherwise the FortiGate would replace the
   entire list on every pull and active sessions would break. Stale IPs
   are acceptable because this is an allowlist.
4. **Commit**: `feed.txt` is committed only when it changed
   (commit style: Conventional Commits).

**Deletions** can only happen on a reset: if the union exceeds the cap
(`max=5000` lines), the list is reset to the fresh resolutions only
(log: `Union exceeds 5000, reset to fresh resolutions`). FortiGate
dynamic addresses support up to 100,000 IPv4 addresses, so the
headroom is large.

## FortiGate

**GUI:** System > Security Fabric > External Connectors > Create New >
IP address

- Name: `HUNTRESS`
- Update method: Pull
- URL: `https://raw.githubusercontent.com/<OWNER>/Huntress-Fortigate-AddressFeed/main/feed.txt`
- Interval: `1800` (s)

The feed creates a dynamic address object (name = feed name) that is
used as `dstaddr` in the outbound policy (service TCP 443). Check the
status (last successful pull, errors) in the connector view.

## Maintaining domains

- Add/remove domains: edit `sources.txt` and push – everything else
  happens automatically.
- No wildcards (`*.domain`) and no paths (`domain.com/path`) – exact
  DNS names only.
- Source of the domain list: the Huntress documentation
  (agent/update/CDN/S3/Azure/blob/bugsnag/GitHub). When Huntress
  releases product updates, re-check the list there.

## Limitations

- **Shared IP pools**: S3, Azure Blob, and GitHub (CloudFront) use
  shared/rotating IP pools. The feed therefore covers more than the
  Huntress domains alone (broader egress, acceptable for an agent
  allowlist).
- **Vantage point**: resolution happens on GitHub runners (cloud
  resolvers), not from our DC – the observed IP subsets may differ
  from the FortiGate's perspective. The merge logic compensates for
  this.
- **Freshness**: IP changes become effective after the cron + FortiGate
  pull interval (worst case ~2 h + 30 min).
- **IPv6**: not supported – dynamic FortiGate addresses are populated
  with IPv4 only.
